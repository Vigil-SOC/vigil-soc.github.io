Production-style Helm chart for the Vigil SOC platform. Ships the backend API
(with bundled SPA), the autonomous SOC daemon, the LLM worker, the agent
worker and agent serve, the MCP runner, the agent shell, the Bifrost LLM
gateway, and in-cluster Postgres + Redis as a single release.

## TL;DR

```bash
helm install vigil ./infra/helm/vigil \
  --namespace vigil --create-namespace \
  --set secrets.anthropicApiKey=$ANTHROPIC_API_KEY \
  --set secrets.postgresPassword=$(openssl rand -hex 24) \
  --set secrets.vigilAppPassword=$(openssl rand -hex 24) \
  --set secrets.jwtSecretKey=$(python3 -c "import secrets; print(secrets.token_urlsafe(64))") \
  --set secrets.agentInternalToken=$(python3 -c "import secrets; print(secrets.token_urlsafe(48))") \
  --set upgrade.acknowledgeVersion=1.1.2 \
  --set upgrade.acknowledgeReason="initial install"
```

For a dev install with auth bypass:

```bash
helm install vigil ./infra/helm/vigil \
  -f ./infra/helm/vigil/values-dev.yaml \
  --namespace vigil --create-namespace \
  --set secrets.anthropicApiKey=$ANTHROPIC_API_KEY
```

Then port-forward the backend to try it out:

```bash
kubectl port-forward -n vigil svc/vigil-backend 6987:6987
# open http://localhost:6987
```

## What gets deployed

| Workload | Kind | Replicas | Notes |
|---|---|---|---|
| `vigil-backend` | Deployment | 2 (default) | FastAPI API + bundled SPA on port 6987 |
| `vigil-daemon` | StatefulSet | **1 (singleton)** | Autonomous orchestrator; webhook=8081, metrics=9090, health=9091 |
| `vigil-llm-worker` | Deployment | 2 (default) | ARQ worker for Claude requests off Redis queue |
| `vigil-agent-worker` | Deployment | 2 (default) | Drains the BullMQ `agent-runs` queue; probes on 6990, no Service. Opt-out via `agentWorker.enabled=false` |
| `vigil-agent-serve` | Deployment | 2 (default) | Agent chat (SSE) and run projections on 6989; ClusterIP, reached by the backend at `AGENT_URL`. Opt-out via `agentServe.enabled=false` |
| `vigil-mcp-runner` | Deployment | 1 | MCP servers over streamable HTTP on port 6991. Opt-out via `mcpRunner.enabled=false` |
| `vigil-agent-shell` | Deployment | 1 | Runs the agent image's `node dist/shell.js` on port 6992, behind the backend's `read_case_shell` tool at `SHELL_URL`. Opt-out via `agentShell.enabled=false` |
| `vigil-bifrost` | StatefulSet | 1 | LLM gateway on port 8080; backend, daemon, LLM worker, agent worker, and agent serve all receive `BIFROST_URL`. Opt-out via `bifrost.enabled=false` and set `config.BIFROST_URL` to your own gateway |
| `vigil-postgres` | StatefulSet | 1 | Opt-out via `postgresql.enabled=false` |
| `vigil-redis` | StatefulSet | 1 | Opt-out via `redis.enabled=false` |

### Images

Four Vigil images are published per release. `vigil-agent-worker`,
`vigil-agent-serve`, and `vigil-agent-shell` run the **same** image with
different commands — it is a Node image and cannot reuse the backend's the
way `llm-worker` does.

| Image | Used by |
|---|---|
| `ghcr.io/vigil-soc/vigil-backend` | backend, llm-worker |
| `ghcr.io/vigil-soc/vigil-daemon` | daemon |
| `ghcr.io/vigil-soc/vigil-agent` | agent-worker, agent-serve, agent-shell |
| `ghcr.io/vigil-soc/vigil-mcp-runner` | mcp-runner |

If you mirror images into a private registry or run air-gapped, mirror all
four Vigil images — the agent Deployments and the MCP runner are enabled by
default and will otherwise sit in `ImagePullBackOff`. Also mirror the
third-party images the chart pulls by default: `postgres:16-alpine`,
`redis:7-alpine`, and `maximhq/bifrost:v2.2.1`. To upgrade without the agent
Deployments, set `agentWorker.enabled=false` and `agentServe.enabled=false`.

## Required inputs

At minimum you need:

- `secrets.anthropicApiKey` — Claude API key for AI agents
- `secrets.postgresPassword` — used for the in-chart Postgres; skip if using an external DB with `postgresql.auth.existingSecret` or `postgresql.external.existingSecret`
- `secrets.vigilAppPassword` — required when `secrets.existingSecret` is not set; the `vigil_app` password, and it must differ from `secrets.postgresPassword`
- `secrets.vigilAgentPassword` — the `vigil_agent` password; generated by the chart if unset, but set it explicitly under `helm template` or a GitOps controller, where the chart's lookup cannot preserve a generated value

When `config.DEV_MODE=false` (the default), also set:

- `secrets.jwtSecretKey` — generate with `python -c "import secrets; print(secrets.token_urlsafe(64))"`

When the agent Deployments are enabled (the default), also set:

- `secrets.agentInternalToken` — generate with `python -c "import secrets; print(secrets.token_urlsafe(48))"`. It is the whole gate on the seam between the backend and the agent layer since ADR 0014, and it fails closed: leave it unset and every `/internal` call answers 503 and every non-health agent call answers 401, so no run gets past resolving its playbook.

On install and on every upgrade you must also set the upgrade
acknowledgement (see [Upgrades](#upgrades)):

- `upgrade.acknowledgeVersion` — this release's version (for example `1.1.2`)
- `upgrade.acknowledgeReason` — why you are upgrading without a Vigil restore point

## External Postgres or Redis

Point the chart at existing infrastructure instead of running in-cluster:

```yaml
postgresql:
  enabled: false
  external:
    host: my-rds.example.com
    port: 5432
    database: deeptempo_soc
    username: deeptempo
    existingSecret: my-rds-credentials
    existingSecretKey: password

redis:
  enabled: false
  external:
    url: "rediss://:password@my-elasticache.example.com:6379/0"
```

The `database` and `username` above match the chart's defaults; set them to
whatever your external database actually uses. To require SSL for the
external database, set `POSTGRES_SSL_MODE=require` via `extraConfig` /
`extraEnv` — the chart injects discrete `POSTGRES_*` variables, not a DSN.

## Pre-created Secret

If you manage secrets with ExternalSecrets Operator, SOPS, or Sealed Secrets,
create the Secret yourself and point the chart at it:

```yaml
secrets:
  existingSecret: vigil-secrets
```

The Secret must define keys matching env var names:
`ANTHROPIC_API_KEY`, `POSTGRES_APP_PASSWORD`, `POSTGRES_AGENT_PASSWORD`,
`JWT_SECRET_KEY`, plus `MCP_RUNNER_TOKEN` and `SHELL_TOKEN` for the MCP
runner and agent shell, plus whichever integration creds you use
(`SPLUNK_PASSWORD`, `SLACK_BOT_TOKEN`, …). The database owner password flows
separately via `postgresql.auth.existingSecret` /
`postgresql.external.existingSecret`.

## Upgrades

Schema is owned by `python -m core.upgrade`, run by Jobs in the chart — there
is no separate init-SQL job. On upgrade, a pre-upgrade Job first runs
`--check`; then a second Job scales every Deployment and StatefulSet of the
release except Postgres and Redis to 0, runs the upgrade, and Helm rolls out
the new pods. The release is down from the scale-down until Helm has rolled
out the new pods, and source events are not queued meanwhile: plan a
maintenance window, and set `--timeout` to cover it.

Helm takes no Vigil backup. The acknowledgement below stands in for the
restore point, so both values are required on install and on every upgrade;
the upgrade Jobs refuse to run without them:

```bash
helm upgrade vigil ./infra/helm/vigil -n vigil --reuse-values \
  --set upgrade.acknowledgeVersion=1.1.2 \
  --set upgrade.acknowledgeReason="nightly RDS snapshot 2026-10-22" \
  --timeout 15m
```

Set `upgrade.enabled=false` to render none of the upgrade Jobs and run
`python -m core.upgrade` as the database owner yourself.

The chart's default image tag resolves to `Chart.AppVersion`, which
release-please bumps in lockstep with the chart `version` on every
release — so a `helm upgrade` after pulling the new chart version
picks up the matching images automatically. Override only if you need
to pin to a different tag than the chart's `appVersion` (for example,
to deploy a `:latest` build for testing):

```bash
helm upgrade vigil ./infra/helm/vigil -n vigil --reuse-values \
  --set upgrade.acknowledgeVersion=1.1.2 \
  --set upgrade.acknowledgeReason="nightly RDS snapshot 2026-10-22" \
  --set backend.image.tag=latest \
  --set daemon.image.tag=latest
```

## Values reference

See `values.yaml` for the full schema. Non-obvious choices:

- **Daemon singleton**: `replicas: 1` is hardcoded in `daemon-statefulset.yaml`
  because the orchestrator holds in-memory state. Do not template this.
- **LLM worker image**: inherits from `backend.image` unless
  `llmWorker.image.repository` is set. The only difference at runtime is the
  entrypoint (`services.worker`).
- **Daemon probes**: target port `9091` (`/health`), not `9090`. Port `9090`
  is the Prometheus `/metrics` port, which is only served when
  `config.VIGIL_OTEL_ENABLED=true`.

## Optional features (all off by default)

| Feature | Flag | Notes |
|---|---|---|
| NetworkPolicies | `networkPolicies.enabled` | Default-deny + per-component allow rules |
| Prometheus ServiceMonitor | `observability.serviceMonitor.enabled` | Requires Prometheus Operator CRDs |
| ExternalSecrets | `secrets.externalSecret.enabled` | Pulls from AWS SM / Vault / GCP SM |
| Bitnami postgres subchart | `postgresql.bitnami.enabled` | Run `helm dependency update` once |
| Bitnami redis subchart | `redis.bitnami.enabled` | Same |
| OTEL Collector subchart | `otelCollector.enabled` | In-cluster OTLP endpoint |
| KEDA queue-depth autoscaling | `llmWorker.autoscaling.keda.enabled` | Requires KEDA operator |
| Splunk | `splunk.enabled` | Standalone StatefulSet; dev/demo only |
| pgAdmin | `pgadmin.enabled` | Standalone Deployment; dev/demo only |

See the chart's [README.md](https://github.com/Vigil-SOC/vigil/blob/main/infra/helm/vigil/README.md) for end-to-end examples of each.

## Development

```bash
# Lint
helm lint infra/helm/vigil --set secrets.postgresPassword=test-password,secrets.vigilAppPassword=test-app-password
helm lint infra/helm/vigil -f infra/helm/vigil/values-dev.yaml

# Render without applying
helm template vigil infra/helm/vigil \
  --set secrets.anthropicApiKey=test \
  --set secrets.postgresPassword=test-password,secrets.vigilAppPassword=test-app-password

# Dry-run install
helm install --dry-run --debug vigil infra/helm/vigil \
  --set secrets.anthropicApiKey=test \
  --set secrets.postgresPassword=test-password,secrets.vigilAppPassword=test-app-password
```

### Schema upgrades

There are no bundled init-SQL copies to keep in sync. Schema is owned by the
`python -m core.upgrade` Jobs described in [Upgrades](#upgrades); see
`docs/upgrading.md` in the code repository for the upgrade mechanism.
